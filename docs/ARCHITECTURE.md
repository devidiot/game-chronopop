# ChronoPop — 코드 구조

의존성 없는 TypeScript + Canvas 2D. 빌드 결과는 JS 49KB(gzip 16KB) 남짓이다.

## 파일

```
src/
  main.ts              조립과 게임 루프 — 엔진·렌더러·UI를 연결한다
  style.css            HUD와 오버레이 스타일

  game/                브라우저 API에 의존하지 않는 순수 로직
    config.ts          모든 밸런스 상수와 젬 색·모양 정의 (보드 크기는 가변)
    types.ts           Tile, Grid, MatchGroup, Phase 등
    board.ts           보드 생성·스왑·중력·셔플·힌트 탐색
    match.ts           3연속 탐색과 덩어리 묶기(BFS)
    scoring.ts         점수·시간 보상 계산
    engine.ts          게임 상태 기계 (아래 참고)
    storage.ts         기록·설정 저장 (localStorage, 기록은 보드 크기별)
    audio.ts           WebAudio 합성 효과음 — 오디오 파일 없음

  render/
    renderer.ts        보드 배경·젬 배치·페이즈별 보간
    gems.ts            젬 한 개를 그리는 코드 (그라디언트·광택·글로우)
    effects.ts         파티클·링 웨이브·떠오르는 점수 글자

  input/
    pointer.ts         드래그/탭 조작을 격자 좌표로 변환

  ui/
    screens.ts         HUD 갱신과 오버레이 화면 전환

test/
  sim.ts               밸런스 시뮬레이터 (렌더링 없이 엔진만 구동)

scripts/
  make-icons.mjs       PNG 아이콘 생성기 (외부 라이브러리 없이 픽셀 직접 계산)
  inline-single.mjs    dist를 단일 HTML 파일로 합치기
  precache-sw.mjs      빌드 산출물 목록을 서비스 워커에 주입 (오프라인 실행용)
  build-apk.mjs        안드로이드 디버그 APK 빌드
  simulate.mjs         sim.ts를 esbuild로 묶어 Node에서 실행
```

## 상태 기계

`Engine.phase` 하나로 전체 흐름이 결정된다. 각 페이즈는 정해진 시간(`dur`)
동안 지속되고, 끝나면 다음 페이즈로 넘어간다.

```
        title
          │ start()
          ▼
   ┌──► idle ──────────────┐  (입력 대기, 여기서만 조작을 받는다)
   │      │                │
   │      │ trySwap()      │ 둘 곳이 없으면 → shuffle ──┐
   │      │                │                            │
   │      │ useChance()    │                            │
   │      │      └──► chance ─ 매치 없음 ────────────────┤
   │      ▼                        │                    │
   │    swap                       │ 매치 있음           │
   │      │                        │                    │
   │      ├─ 매치 없음 → swapback ──┼────────────────────┤
   │      │                        │                    │
   │      └─ 매치 있음              │                    │
   │           ▼                   ▼                    │
   │         clear ◄───────────────┘                    │
   │           │         ▲                              │
   │           ▼         │ (또 매치되면 연쇄)             │
   │         fall ───────┘                              │
   │           │                                        │
   └───────────┴────────────────────────────────────────┘

  어느 페이즈에서든 시간이 0이 되면 → over
```

- `clear` 진입 시점에 점수와 시간이 **즉시** 반영된다. 연출이 끝나기를
  기다리지 않으므로 조작감이 늦게 느껴지지 않는다.
- `fall` 이 끝날 때 다시 매치를 찾아 있으면 `chain`을 올리고 `clear`로 돌아간다.
  이 순환이 연쇄다.
- 셔플은 **먼저 재배치한 뒤** 연출을 재생한다. 그래야 화면이 갑자기 바뀌지 않는다.

## 엔진과 렌더러의 경계

엔진은 그리지 않고, 렌더러는 판단하지 않는다.

타일은 논리 좌표(`row`/`col`)와 애니메이션 시작 좌표(`fromRow`/`fromCol`)를
함께 들고 있다. 엔진이 이 둘과 `phase`/`progress`를 남기면, 렌더러는
페이즈에 맞는 곡선으로 보간만 한다.

```ts
// renderer.ts — fall 페이즈
const e = fallEase(progress);
visualRow = tile.fromRow + (tile.row - tile.fromRow) * e;
```

덕분에 엔진은 DOM/Canvas 없이 Node에서 그대로 돌아가고, 그래서
`test/sim.ts` 같은 시뮬레이터를 쉽게 붙일 수 있다.

## 성능 — 휴대폰이 뜨거워지지 않게

젬 하나를 그리는 데는 그라디언트 3개, 클리핑, 그림자 블러가 들어간다.
이걸 매 프레임 64번 반복하면 발열이 심해서, 다음 네 가지를 적용했다.

| 대상           | 이전                                  | 지금                     |
| -------------- | ------------------------------------- | ------------------------ |
| 동물 얼굴      | 매 프레임 그라디언트·클립·글로우 × 64 | 종류별 1회 → `drawImage` |
| 보드 바닥      | 매 프레임 그라디언트 3개 + 칸 64개    | 1회 → `drawImage`        |
| 화면 배율      | 최대 3배 (아이폰 기준 1170² 픽셀)     | 최대 2배 (780² 픽셀)     |
| 대기 중 프레임 | 60fps                                 | 20fps                    |
| HUD 갱신       | 매 프레임 DOM 쓰기                    | 0.1초에 한 번            |
| 파티클         | 상한 없음                             | 260개 (넘치면 오래된 것부터) |

파티클 상한은 피버 때문에 필요하다. 피버 중에는 한 번에 수십 칸이 터져서
상한이 없으면 파티클이 수백 개로 불어난다.

히트스톱은 멈춘 동안 엔진·이펙트·렌더링을 전부 건너뛰므로 **오히려 프레임을 아낀다.**

- 젬 스프라이트는 `render/gems.ts` 가 `종류|폭탄|크기|배율` 키로 캐시한다.
  화면 크기가 바뀌면 `clearGemCache()` 로 통째로 버린다.
- 번쩍임(flash)은 새로 그리지 않고 **같은 스프라이트를 `lighter` 로 덧그려** 표현한다.
- 대기 중 20fps는 `main.ts` 의 `IDLE_FRAME_MS` 로 조절한다. 애니메이션·파티클·
  화면 흔들림이 하나라도 있으면 즉시 60fps로 돌아간다.

그래도 뜨겁다면 `renderer.resize()` 의 배율 상한을 1.5로 낮추거나,
`effects.ts` 의 파티클 수(`burst` 의 `count`)를 줄이면 된다.

## 렌더링 메모

- 캔버스는 `position:absolute; inset:0; margin:auto` 로 중앙 정렬한다.
  문서 흐름에 두면 캔버스 크기가 부모 크기에 영향을 주어 매 프레임 레이아웃이
  커지는 되먹임이 생긴다. `transform`은 화면 흔들림 연출 전용으로 비워둔다.
- 낙하 중인 젬이 보드 밖으로 삐져나오지 않도록 보드 영역으로 클리핑한다.
- 파티클 속도 단위는 **px/ms**다. 셀 크기를 그냥 곱하면 한 프레임 만에
  화면 밖으로 날아간다.
- `dt`는 50ms로 clamp한다. 탭을 백그라운드에 뒀다 돌아와도 시간이
  한꺼번에 깎이지 않는다.

## 보드 크기를 런타임에 바꾸는 법

`COLS`/`ROWS` 는 `config.ts` 의 **모듈 변수**(`export let`)다. `setBoardSize()`
가 이 둘을 다시 대입하면, ES 모듈의 import 는 값 복사가 아니라 살아 있는
참조이므로 `board.ts` · `match.ts` · `engine.ts` · `renderer.ts` 가 곧바로
새 값을 본다. 크기를 함수 인자로 줄줄이 넘기지 않아도 되는 이유다.

지켜야 할 것 두 가지.

1. **함수 안에서 읽어야 한다.** 모듈 최상단에서 `const { COLS } = config` 처럼
   꺼내 두면 그 시점의 값이 박제된다.
2. **판이 도는 중에는 바꾸지 않는다.** 크기를 바꾸면 보드를 새로 깔아야 하므로
   `Engine.reset()` 은 `isPlaying` 이면 아무것도 하지 않는다. 크기 선택 UI도
   타이틀에만 있다.

바꾼 뒤에는 `layout()` → `Renderer.resize()` 를 불러 칸 크기와 젬 스프라이트
캐시를 다시 만들어야 한다. `main.ts` 의 `applyBoardSize()` 가 이 순서를 담당한다.
